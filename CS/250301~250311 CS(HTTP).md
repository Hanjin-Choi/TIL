# 인터넷 네트워크
* 인터넷 통신
    * 클라이언트와 서버는 인터넷이라는 망에 의해서 연결되어 있음
## IP
* 지정한 IP 주소에 데이터 전달
* 패킷이라는 통신 단위로 데이터 전달
* 출발지 IP, 목적지 IP, 메시지
* 클라이언트 패킷 전달 : 목적지 IP를 비교하면서 목적지를 찾아가는 구조
* 서버 패킷 전달 : 출발지 IP는 서버 IP, 목적지는 클라이언트로 바껴서 전달
* IP 프로토콜은 한계가 명확함
    * 비연결성 : 패킷을 받을 대상이 없거나 서비스가 불가능해도 패킷을 전송
    * 비신뢰성 : 패킷이 순서대로 안오거나 중간에 사라져도 확인이 불가능
    * 같은 IP를 사용하는 서버에서 둘이상의 프로그램 구분이 어려움

## TCP
* TCP는 IP의 단점을 해결해줌
* 인터넷 프로토콜 스택의 4계층
    * 애플리케이션 계층 : HTTP, FTP
    * 전송계층 : TCP, UDP
    * 인터넷 계층 : IP
    * 네트워크 인터페이스 계층
* 패킷 : 패키지 + 버킷의 합성어
* TCP의 특징
    * 연결지향 : TCP 3 way handshake (가상 연결)
    * 데이터 전달 보증
    * 순서 보장 : 패킷의 순서가 보장됨
    * 신뢰할 수 있는 프로토콜 

### 3-way handshake
1. 클라이언트트에서 sync 신호 전송
2. 서버에서 Sync수신후 ack신호와 함께 전송==sync+ack
3. 클라이언트에서 ack 신호를 수신후 ack를 보냄
4. 데이터 전송
* 3-way handshake를 통해 클라이언트와 서버의 신뢰성 확보 가능해짐
* 최근에는 클라이언트에서 ack 신호를 보낼 때 데이터도 전송함
* 실제로 연결하는 것이 아니라 논리적으로 연결하는 것(전용 LAN이 생기는 것이 아님)

## UDP
* UDP는 IP에서 Port를 추가한 개념
* 기능이 거의 없고 TCP와 같이 연결지향이나, 데이터전달 보증, 순서 보장이 없음
* 하나의 IP에서 여러 정보를 받기 위한 Port
* TCP는 전송속도를 빠르게 만들기 어렵지만 UDP는 더 빠르게 가능함
* 최근에 UDP가 각광받고 있음(HTTP3 protocol에서 속도를 올리려고 하다보니 TCP가 한계가 생기기 때문)

## Port
* 하나의 IP에 여러개의 서버와 통신하기 위해서 Port가 필요함
* 0~65535 할당가능
* 0~1023 은 잘 알려진 포트로 설정하지 않는 것을 권장
    * FTP : 20,21
    * TELNET : 23
    * HTTP : 80
    * HTTPS : 443

## DNS
* IP는 기억하기 어려운 단점이 있고 IP는 변경될 가능성이 높기 때문에 주소를 정해놓는 것
* Domain Name System
* 도메인 주소를 사서 등록하는 시스템, 도메인이 IP로 변경되어 서비스를 이용할 수 있도록 만들어줌


## URI(Uniform Resource Identifier)
* 리소스를 식별하는 통합된 방법
* URN,URL ⊂ URI
* 자원을 식별하는 방법에는 크게 URL, URN이 있음
    * 리소스의 위치를 나타내는 URL, 리소스의 이름을 나타내는 URN
    * url의 예시 / foo://example.com:8042/over/there?name=face#eyes
    * urn의 예시 / urn:example:animal:face:eyes
    * 이름을 부여하면 찾기가 어려워 URL위주로 사용
* Uniform : 리소스 식별하는 통일된 방식
* Resource : 자원, URI로 식별할 수 있는 모든것
* Identifier : 다른 항목과 구분하는데 필요한 정보
* 위치는 변할수 있지만, 이름은 변하지 않음
* URN 이름만으로 실제 리소스를 찾을 수 있는 방법이 보편화되지 않음

### URL의 구성

* scheme://[userinfo@]host[:post][/path][?query][#fragment]
* https://www.google.com:443/search?q=hello&hl=ko

#### scheme
* 주로 프로토콜을 사용
* http는 80포트, https는 443포트를 주로 사용하고 포트는 생략이 가능
* https는 http에 보안을 추가한 것

#### userinfo
* URL에 사용자 정보를 포함해서 인증할 때 사용
* 거의 사용하지 않음

#### path
* 리소스가 있는 경로를 말하고 보통 계층적 구조로 되어있음
* /home/file.png
* /users
* /users/100, /items/iphone12mini

#### query
* key=value형태로 표기
* ?로 시작하고 &로 여러개를 추가할 수 있음
    * ?key1=value1&key2=value2
* query parameter, query string 등으로 불림, 웹서버에 제공하는 문자 형태의 파라미터

#### fragment
* html 내부 북마크 등에 사용하고 서버에 전송하는 정보가 아님

## 웹 브라우저 요청 흐름
* 보통 인터넷 주소를 입력하면 dns를 조회해서 ip와 포트 정보를 찾아내서 Http 요청 메시지를 생성함
* 그 후, Socket 라이브러리를 통해 OS의 TCP/IP에 http 메시지를 전달
* OS에서 TCP/IP 패킷을 생성되어 서버로 전달


# HTTP(HyperText Transfer Protocol)
* 문서간의 링크를 통해 연결할 수 있는 HTML로 시작
* 현재는 모든것을 HTTP에 담아서 전달


## HTTP의 역사
* HTTP/0.9 1991년 : GET메서드만 지원, HTTP 헤더 X
* HTTP/1.0 1996년 : 메서드, 헤더 추가
* HTTP/1.1 1997년 : 가장 많이 사용하는 버전
    * RFC2068(1997) -> RFC2616(1999) -> RFC7230~7235(2014)
* HTTP/2 2015년 : 성능개선
* HTTP/3 진행중 : TCP 대신에 UDP 사용, 성능 개선

## 기반 프로토콜
* TCP : HTTP/1.1, HTTP/2
* UDP : HTTP/3
* 현재 HTTP/1.1 주로 사용
    * HTTP/2, HTTP/3도 점점 증가하는 중

## HTTP 특징
* 클라이언트 서버 구조
* 무상태 프로토콜(스테이트리스), 비연결성
* HTTP메시지
* 단순함, 확장 가능

 ### 클라이언트 서버 구조
 * Request Response 구조
 * 클라이언트는 서버에 요청을 보내고, 응답을 대기
 * 서버가 요청에 대한 결과를 만들어서 응답
 * 클라이언트와 서버를 분리하는 것은 굉장히 중요함
    * 클라이언트는 사용성, UI에 집중하고
    * 서버는 데이터의 흐름에 집중할 수 있음

### 무상태 프로토콜(stateless)
* 서버가 클라이언트의 상태를 보존하지 않음
* 서버 확장성이 높음(스케일 아웃)
* 반면에 클라이언트가 추가 데이터를 전송하는 단점이 있음

#### Stateful, Stateless
* Stateful은 상태를 유지한다는 뜻
    * 서버가 클라이언트의 이전상태(문맥과 유사)를 기억하고 있기 때문에 연속적, 순차적으로 진행이 가능
    * 물건을 사는 과정에서 물건의 종류, 수량, 구매방법을 하나씩 설정이 가능
* Stateless는 상태를 유지하지 않기 때문에 매번 정보를 다시 제공해줘야 함
    * 물건을 사는 과정에서 물건의 종류, 수량, 구매방법을 동시에 제공해야 구매 가능

* 무상태는 응답 서버를 쉽게 바꿀 수 있기 때문에 확장 가능성이 훨씬 좋아짐(수평확장성이 좋음)
    * 클라이언트 요청이 많아지면 서버를 대거 투입이 가능함

#### Stateless의 한계
* 로그인과 같이 상태를 유지해야되는 경우 한계가 있음
* 이러한 경우 상태유지를 브라우저 쿠키와 서버 세션을 사용해서 최소한으로 사용

### 비연결성(connectionless)
* TCP/IP는 보통 연결을 유지함
* 3개의 클라이언트가 1개의 서버와 연결을 할 경우, TCP/IP 구조상 1개의 클라이언트만 사용하여도 나머지 2개가 계속 연결이 유지되고 있기 때문에 서버의 자원을 계속해서 소모하게 됨
* HTTP는 이러한 연결을 유지하지 않는 모델
* 일반적으로 초단위 이하의 빠른 속도로 응답하기 위해서 이렇게 설계되어있음
    * 1시간 동안 수천명이 서비스를 사용해도 실제 서버에서 처리하는 요청은 수십개로 적게 만들은 형태
    * 자원을 효율적으로 사용 가능함

#### 비연결성의 한계
* TCP/IP 연결을 새로 맺어야 함 - 3 way handshake 시간 추가
* 웹 브라우저로 사이트로 요청하면 HTML 뿐만 아니라 자바스크립트, css, 추가 이미지 등 수 많은 자원이 함께 다운로드
* 지금은 HTTP 지속 연결(Persistent Connections)로 문제 해결
* HTTP/2, HTTP/3에서 더 많은 최적화됨

* 서버 개발자들은 같은 시간에 딱 맞춰 발생하는 대용량 트래픽 이벤트를 관리하기 어려움
    * 예를 들어 선착순 이벤트, 명절 KTX예약, 학과 수업 등록
    * 비연결성이 소용이 없음, 한번에 트래픽이 발생하므로
    * 하지만 최대한 스테이트리스를 만들어야함


### HTTP 메시지
* HTTP 메시지 구조 : start-line -> header -> empty-line(CRLF) -> message body

#### 시작라인
* start-line = request-line + status-line

> GET /search?q=hello&hl=ko HTTP/1.1(start-line)
Host: www.google.com(header)
* request-line = method SP(공백) request-target SP HTTP-version CRLF(엔터)

    * HTTP 메서드
        * GET : 조회
        * PUT : 수정
        * POST : 요청 내역 처리
        * DELETE : 삭제
    * 요청대상 (/search?q=hello&hl=ko)
        * 절대경로와 쿼리를 합쳐서 만듦
        * 절대경로 : '/'로 시작하는 경로
    * HTTP Version
* status-line = HTTP-version SP status-code SP reason-phrase CRLF
    * HTTP 버전
    * HTTP 상태 코드
        * 200 : 성공
        * 400 : 클라이언트 요청 오류
        * 500 : 서버 내부 오류
    * 이유 문구 : 사람이 이해할 수 있는 짧은 상태 코드 설명 글

#### 헤더
* header-field = field-name ":" OWS field-value OWS (OWS:띄어쓰기 허용)
* field-name 은 대소문자 구분 없음
* HTTP 전송에 필요한 모든 부가 정보
    * 메시지 바디의 내용
    * 메시지 바디의 크기, 압축, 인증, 요청 클라이언트(브라우저) 정보
    * 서버 애플리케이션 정보
    * 캐시관리 정보

#### 메시지 body
* 실제 전송할 데이터
* 바이트로 표현할 수 있는 모든 데이터(HTML 문서, 이미지, 영상, JSON)

## HTTP 메서드
* 좋은 URI 설계란?
    * 리소스로 식별하는 것
    * 리소스 : 회원을 관리하는 API에서 회원이라는 개념이 리소스
    * 좋은 URI를 설계하기 위해서는 리소스와 행위를 분리해야함
* 리소스는 명사, 행위는 동사
* 행위는 메서드로 구분
### HTTP 메서드 종류
* GET : 리소스 조회
* POST : 요청 데이터 처리, 주로 등록에 사용
* PUT : 리소스를 대체, 해당 리소스가 없으면 생성
* PATCH : 리소스 부분 변경
* DELETE : 리소스 삭제
* HEAD : GET과 동일하지만 메시지 부분을 제외하고, 상태 줄과 헤더만 반환
* OPTIONS : 대상 리소스에 대한 통신 가능옵션(메서드)을 설명(주로 CORS에서 사용)
* CONNECT : 대상 자원으로 식별되는 서버에 대한 터널을 설정
* TRACE : 대상 리소스에 대한 경로를 따라 메시지 루프백 테스트를 수행

#### GET
* 리소스 조회
* 서버에 전달하고 싶은 데이터는 query(쿼리 파라미터, 쿼리 스트링)를 통해서 전달
* 메시지 바디를 사용해서 데이터를 전달할 수 있지만, 지원하지 않는 곳이 많아서 권장하지 않음
* GET을 요청하면 캐싱이 가능

#### POST
* 요청데이터 처리
    * 새 리소스 생성
    * 단순히 데이터를 생성하거나, 변경하는 것을 넘어서 프로세스를 처리해야 하는 경우
        * 주문에서 결제완료 -> 배달시작 -> 배달 완료처럼 단순히 값 변경을 넘어 프로세스의 상태가 변경되는 경우
    * 다른 메서드로 처리하기 애매한 경우
* 메시지 바디를 통해 서버로 요청 데이터 전달
* 서버는 요청 데이터를 처리하는
    * 메시지 바디를 통해 들어온 데이터를 처리하는 모든 기능을 수행
* 신규 리소스 등록, 프로세스 처리에 사용

#### PUT
* 기존 리소스를 삭제하고 대체하는 데 사용
* 기존 리소스가 없으면 생성하는 역할
* 클라이언트가 리소스를 식별한다는 점에서 POST와 차이가 있음

#### PATCH
* 기존 리소스를 부분 변경하는 데 사용
* 전체를 덮어버리는 PUT과 다름
* HTTP에서 PATCH를 못 인식하는 경우가 있는데 이때는 POST를 사용하면 됨.


## HTTP 메서드 속성
* 안전(Safe Methods)
    * 호출해도 리소스의 변경이 없다
    * GET, HEAD
* 멱등(Idempotent Methods)
    * 한번이상의 호출은 항상 결과가 똑같음
    * f(f(x))=f(x)
    * GET, PUT, DELETE
    * POST는 아님
    * 자동복구 메커니즘에 사용(DELETE가 안됐다고 생각하면 DELETE를 한번 더 해도 됨 )
* 캐시가능(Cacheable Methods)
    * 응답결과 리소스를 브라우저에 저장
    * GET, HEAD, POST, PATCH 캐시 가능
    * 하지만 실제로는 GET, HEAD만 캐시로 사용
        * POST, PATCH는 본문 내용까지 캐시 키로 고려해야 되기 때문에 구현이 어려워 잘 사용하지 않음

## HTTP 메서드 활용
* 클라이언트에서 서버로 데이터 전송에 사용됨
* 데이터를 전송하는 방식은 크게 2가지로 분류
    * 쿼리 파라미터를 통한 데이터 전송
        * 대표적으로 GET이 있음, Key-Value 형태
    * 메시지 바디를 통한 데이터 전송
        * POST, PUT, PATCH
* 클라이언트에서 서버로 데이터 전송하는 상황은 크게 4가지
    * 정적 데이터 조회
        * 이미지, 정적 텍스트 문서와 같은 정적 데이터는 GET을 사용해서 조회
        * 일반적으로 쿼리 파라미터 없이 리소스 경로를 통해 단순하게 조회가 가능
    * 동적 데이터 조회
        * 주로 검색, 게시판 목록에서 정렬 필터(검색어)기능을 구현하기 위해서 쿼리 파라미터를 사용
        * GET을 사용해서 조회
    * HTML Form을 통한 데이터 전송
        * 회원가입, 상품주문, 데이터 변경을 구현하기 위해 POST를 사용해서 메시지 바디에 데이터를 담아서 전송
        * GET으로도 전송할 수 있음, 하지만 조회용
        * multipart/form-data는 파일 전송도 가능(주로 바이너리 데이터(ex. 이미지)를 전송==파일 업로드)

    * HTTP API를 통한 데이터 전송
        * 서버에서 서버, 클라이언트로 모든 메서드 활용하여 데이터 전송 가능
        * Content-Type은 Json을 사용해서 전송


### HTTP API 설계
#### 회원관리
* 회원 목록 /members : GET
* 회원 등록 /members : POST
* 회원 조회 /members/{id} : GET
* 회원 수정 /members/{id} : PATCH, PUT,POST
* 회원 삭제 /members/{id} : DELETE
* POST기반의 신규자원 등록방법

#### 파일 관리
* 파일 목록 /files : GET
* 파일 조회 /files/{filename} : GET
* 파일 등록 /files/{filename} : PUT, 클라이언트가 리소스URI를 알아야함
* 파일 삭제 /files/{filename} : DELETE
* 파일 대량 등록 /files : POST
* 스토어 : 클라이언트가 관리하는 리소스 저장소, 클라이언트가 리소스의 URI를 알고 관리
    * 위의 예시에서 스토어는 /files

#### HTML Form
* HTML Form은 GET, POST만을 사용 가능
* 회원 목록 /members : GET
* 회원 등록 폼 /members/new : GET
* 회원 등록 /members/new, /members : POST
* 회원 조회 /members/{id} : GET
* 회원 수정 폼 /members/{id}/edit : GET
* 회원 수정 /members/{id}/edit, /members/{id} : POST
* 회원 삭제 /members/{id}/delete : POST
* GET, POST 제약으로 인해 컨트롤 URI를 사용
    * 동사로 된 리소스 경로를 통해 /edit, /new, /delete를 POST로 구현

#### 참고하면 좋은 설계법
* https://restfulapi.net/resource-naming

* 문서
    * 단일개념(파일 하나, 객체 인스턴스, 데이터 베이스 row)
    * /members/100
* 컬렉션
    * 서버가 관리하는 리소스 디렉터리
    * 서버가 리소스의 URI를 생성하고 관리
    * /members
* 스토어
    * 클라이언트가 리소스의 URI를 알고 관리하는 자원 저장소
    * /files
* 컨트롤러, 컨트롤 URI
    * 문서, 컬렉션, 스토어로 해결하기 어려운 추가 프로세스를 설계
    * /members/{id}/delete

## HTTP 상태 코드
* 클라이언트가 보낸 요청의 처리 상태를 응답에서 알려주는 기능
* 100번대(Informational) : 요청이 수신되어 처리중, 거의 사용하지 않음
* 200번대(Successful) : 요청 정상 처리
    * 200 : OK, 요청성공
    * 201 : Created, 요청 성공해서 새로운 리소스가 생성, 주로 POST메서드 사용시 응답
    * 202 : Accepted, 요청이 접수는 되었으나 아직 처리가 완료되지 않음
    * 204 : No Content, 서버가 요청을 성공적으로 수행했지만, 응답 페이로드 본문에 보낼 데이터가 없음. 웹 문서 편집기에서 save 버튼 같은 기능에서 사용.

* 300번대(Redirection) : 요청을 완료하려면 추가 행동이 필요
    * 300대 응답 결과에 Location 헤더가 있으면, Location 위치로 자동 이동\
    * 리다이렉트에는 영구 리다이렉션, 일시 리다이렉션, 특수 리다이렉션이 있음
        * 영구 리다이렉션 : 특정 리소스의 URI가 영구적으로 이동
            * 원래의 URL를 사용하지 않고 검색엔진 등에서도 변경을 인지한 경우에 사용
            * 301 : 리다이렉트시 요청 메서드가 GET으로 변하고, 본문이 제거될 가능성이 있음(새로 다시 입력해야 됨)
            * 308 : 301과 기능은 같지만 리다이렉트시 요청 메서드와 본문 유지(처음 POST를 보내면 리다이렉트도 POST로 전송)
            * 실무에서는 리다이렉트 후 POST로 와도 301처럼 GET으로 변경해서 사용
            
        * 일시 리다이렉션 : 일시적인 변경, PRG(Post/Redirect/Get)
            * 주문 완료 후 주문 내역 화면으로 이동하는 경우
            * 302 : 리다이렉트 시 요청 메서드가 대부분 GET으로 변하고, 본문이 제거될 수 있음
            * 307 : 리다이렉트 요청 메서드와 본문 유지
            * 303 : 리다이렉트시 요청 메서드가 GET으로 변경
            * PRG : 새로고침 시 중복 주문이 들어갈 수 있기 때문에 POST요청이 되면 GET으로 리다이렉트하여 메서드를 변경해줌, 새로고침해도 결과가 중복되지 않음
            * 302를 사용하는 경우가 많아서 애매하지만 문제는 없음
        * 특수 리다이렉션 : 결과 대신 캐시를 사용
            * 304 : Not Modified
            * 캐시를 목적으로 사용
            * 클라이언트에게 리소스가 수정되지 않았음을 알려줌.
            * 클라이언트는 로컬pc에 저장된 캐시를 재사용
    * 300 : Multiple Choice, 거의 안씀
    * 301 : Moved Permanently
    * 302 : Found
    * 303 : See Other
    * 304 : Not Modified
        * 캐시를 목적으로 사용
        * 클라이언트에게 리소스가 수정되지 않았음을 알려줌.
        * 클라이언트는 로컬pc에 저장된 캐시를 재사용
    * 307 : Temporary Redirect
    * 308 : Permanent Redirect
     
* 400번대(Client Error) : 클라이언트 오류, 잘못된 문법등으로 서버가 요청을 수행할 수 없음
    * 똑같은 재시도 시 실패
    * 클라이언트는 요청 내용을 다시 검토하고 보내야함
    * 401 : Unauthorized, 인증이 되지 않음.
        * Authentication : 인증, 본인이 누구인지 확인(로그인)
        * Authorization : 권한부여, Admin 권한처럼 특정 리소스에 접근할 수 있는 권한 인증이 있어야 인가가 있음
    * 403 : Forbidden, 서버가 요청을 이해했지만 승인을 거부, 자격증명은 있지만 접근권한이 없는 경우
    * 404 : Not Found, 요청 리소스를 찾을 수 없음, 권한이 부족한 리소스에 접근할 때에도 숨기고 싶은 경우에 사용

* 500번대(Server Error) : 서버 오류, 서버가 정상 요청을 처리하지 못함
    * 똑같은 재시도를 해도 서버의 상황에 따라 성공할 수 있음
    * 500 : Internal Server Error, 서버 내부 문제
    * 503 : Service Unavailable, 서버가 일시적인 과부하 또는 예정된 작업으로 잠시 요청을 처리 못하는 경우 사용
    * 웬만한 경우 500대 에러가 나오면 안됌

* 모르는 상태 코드가 나온다면 상위 코드로 해석해서 처리하면 됨. 200,300,400,500대로 나눠서 처리.

## HTTP 헤더
* header-field = field-name ":" OWS field-value OWS     (OWS : 띄어쓰기 허용)
* field-name은 대소문자 구분 없음
* HTTP 전송에 필요한 모든 부가정보를 담는 역할
* General 헤더 : 메시지 전체에 적용되는 정보
    * Connection: close
* Request 헤더 : 요청 정보
    * User-Agent: Mozilla/5.0(Macintosh;..)
* Response 헤더: 응답 정보
    * Server: Apache
* Entity 헤더: 엔티티 본문의 데이터를 해석할 수 있는 정보(데이터 유형html인지 json인지, 데이터 길이, 압축정보)를 제공
    * Content-Type: text/html, Content-Length: 3423
    * RFC2616(2019년)에서 RFC7230~7235(2014년)가 등장하면서 엔티티 대신 표현으로 바뀜
    * 표현 = 표현데이터 + 표현 메타데이터, 요청이나 응답에서 전달할 실제 데이터
    * 메시지 본문을 통해 표현 데이터를 전달하며 메시지 본문을 페이로드라고도 부름 
### 표현 헤더
* Content-Type : 표현 데이터의 형식
    * 미디어 타입, 문자 인코딩과 같은 컨텐트 바디에 들어갈 정보들
* Content-Encoding : 표현 데이터의 압축 방식
    * 데이터를 전달하는 곳에서 압축 후 인코딩 헤더 추가
    * 데이터를 읽는 쪽에서 인코딩 헤더의 정보로 압축 해제를 함
    * gzip, deflate, identity(압축 안한다는 뜻)
* Content-Language : 표현 데이터의 자연 언어
    * ko, en, en-US
* Content-Length : 표현 데이터의 길이
    * 바이트 단위
    * Transfer-Encoding(전송 코딩)을 사용하면 Content-Length를 사용하면 안됨
        * 전송코딩에 모든 정보가 들어가기 때문
* 표현 헤더는 전송, 응답 둘다 사용

### 협상헤더(콘텐츠 네고시에이션)
* 클라이언트가 선호하는 표현 요청
* Accept : 클라이언트가 선호하는 미디어 타입 전달
* Accept-Charset : 클라이언트가 선호하는 문자 인코딩
* Accept-Encoding : 클라이언트가 선호하는 압축 인코딩
* Accept-Language : 클라이언트가 선호하는 자연 언어
* 협상 헤더는 요청 시에만 사용
* Quality Values : 협상하는데 우선순위가 필요함
    * 예를 들어, 독일어와 영어를 지원하는 웹사이트에서 한국어를 요청할 경우, 독일어가 그대로 반환될 것인데 유저는 한국어가 안되면 영어로 접근할 의지가 있는 경우에 영어를 자동으로 제공하는 기능이 필요
    * 0~1사이 값으로 클수록 높은 우선순위를 가짐
    * 생략할 경우 1로 적용
    * Accept-Language:ko-KR, ko;9=0.9, en-US;q=0.8,en;q=0.7 이런식으로 헤더를 적용해서 한국어 대신 영어를 지원할 수 있도록 함.
    * 구체적인 것이 우선순위가 높음
        * Accept : text/*, text/plain, text/plain;format=flowed, */*이면 text/plain;format=flowed가 최고 우선순위
    * 구체적인 기준으로 미디어 타입을 맞춤

### 전송 방식
* 단순전송 : 요청하면 데이터를 한번에 전송
* 압축전송 : 컨텐트 인코딩을 포함하여 원래데이터를 압축해서 전송
* 분할전송 : 청크를 나눠서 전송, content-length를 보내지 않음
* 범위전송 : 이미지를 전송할 때, 중간에 끊기는 경우 처음부터 다시 보내지 않는 것처럼 특정 구간부터 데이터를 보내도록 지정

### 일반 정보 헤더
* From : 유저 에이전트의 이메일 정보
    * 일반적으로 잘 사용하지 않지만, 요청에 의해 검색엔진 같은 곳에서 사용
* Referer : 이전 웹페이지 주소, A-> B로 이동시 Referer에 A를 포함해 요청함
    * 요청에 의해 사용, Referer를 통해 유입경로 분석이 가능함
    * Referer는 referrer의 오타인데 이제는 더이상 바꿀수 없어서 그대로 사용중
* User-Agent : 유저 에이전트 애플리케이션 정보
    * 클라이언트의 애플리케이션 정보(웹 브라우저 정보)
    * 통계 처리하는데 사용할 수 있음(특정 브라우저에서 버그가 생기는 경우)
* Server : 요청을 처리하는 오리진 서버의 소프트웨어 정보
    * Server: Apache/2.2.22(Debian)
    * 응답에서 사용
* Date: 메시지가 생성된 날짜
    * 응답에서만 사용

### 특별한 정보 헤더
* Host : 요청한 호스트 정보(도메인)
    * 요청에서 사용하는 필수 헤더
    * 하나의 서버가 여러 도메인을 처리해야할 때나 하나의 IP 주소에 여러 도메인이 적용되어 있을 때 구분하기 위해 사용(IP로 통신하기 때문에)
* Location : 페이지 리다이렉션
    * 웹브라우저에서 300대 응답의 결과에 Location 헤더가 있으면 해당 위치로 리다이렉트
    * 201(created)에도 사용가능
* Allow : 허용 가능한 HTTP 메서드
    * 405(Method Not Allowed)에서 응답에 포함해야함
    * Allow: GET, POST
* Retry-After : 유저 에이전트가 다음 요청을 하기까지 기다 려야 하는 시간
    * 503(Service Unavailable) : 서비스가 언제까지 불능인지 알려줄 수 있음
    * Retry-After : 120 (초단위)
    * Retry-After : Sun, 10 Mar 2025 23:59:59 GMT
    
### 인증 헤더
* Authorization : 클라이언트 인증 정보를 서버에 전달
* WWW-Authenticate : 리소스 접근 시 필요한 인증 방법 정의
    * 401 Unauthorized에 인증에 필요한 정보를 담아서 제공

### 쿠키
* Set-Cookie : 서버에서 클라이언트로 쿠키 전달(응답)
* Cookie : 클라이언트가 서버에서 받은 쿠키를 저장하고, HTTP 요청시 서버로 전달
* 쿠키가 없으면 모든 요청에 사용자 정보가 포함되도록 개발해야함
* 사용처
    * 사용자 로그인 세션 관리
    * 광고 정보 트래킹
* 쿠키 정보는 항상 서버에 전달되기 때문에 네트워크의 트래픽을 추가 유발함
    * 따라서 최소한의 정보만 사용해서 쿠키를 구성하는 것이 중요
    * 서버에 전달하지 않기 위해서는 웹브라우저 내부에 데이터를 저장(웹스토리지)
* 쿠키의 생명주기는 크게 두가지로 구성할 수 있음
    * 세션쿠키 : 만료 날짜를 생략하여 브라우저 종료시까지만 유지
    * 영속쿠키 : 만료 날짜를 입력하여 해당 날짜까지 유지
        * 만료일 기준 : Set-Cookie : expires=Tue, 11-Mar-2025 12:11:11 GMT
            * 항상 GMT 기준으로 작성해야되며 만료일이 되면 쿠키 삭제
        * 시간 기준 : Set-Cookie : max-age=3600
            * 초단위 0이나 음수를 지정하면 쿠키 삭제
* 쿠키는 도메인을 설정할 수 있음
    * 명시 : 명시된 기준 도메인 + 서브 도메인 포함
    * 생략 : 현재 문서 기준 도메인만 적용, 하위 도메인에서는 사용 불가
* 쿠키는 경로를 설정 할 수 있는데 이 경로를 포함한 하위 경로 페이지만 쿠키 접근 가능
* 보완을 위해 3가지를 고려할 수 있음
    * Secure를 넣을 수 있음(HTTPS에서만 사용 가능)
    * HttpOnly
        * XSS공격(Cross Site Scripting)을 막기 위해 설정
        * 자바스크립트에서 접근 불가능
    * SameSite
        * XSRF 공격 방지
        * 요청 도메인과 쿠키에 설정된 도메인이 같은 경우만 쿠키 전송

### 캐시 헤더
* 캐시가 없으면, 데이터가 변경되지 않아도 계속 네트워크를 통해서 데이터를 다운로드 받아야함
    * 브라우저 로딩 속도가 느려짐
* 캐시를 적용하면 캐시 가능 시간동안 네트워크를 사용하지 않아도 되기 때문에 네트워크 사용량을 줄이고 로딩 속도를 빠르게 할 수 있음
#### 검증 헤더와 조건부 요청
* 캐시 유효 시간이 초과해서 서버에 요청해야 되는데 서버에서 데이터가 변경되지 않은 경우, 원래의 캐시 파일을 지우지 않고 다시 사용하는 것이 이득임
    * 이 때 최종 수정 날짜를 브라우저의 헤더에 담아서 서버에 보냈을 때, 서버의 최종 수정일과 동일하다면 304 NOT Modified를 제공하면서 바디를 빼고 전송.(부하를 최소화 시킴)
    * 웹브라우저는 304를 받고 변경되지 않은 사실을 인지하고 캐시를 그대로 사용함
    * 네트워크 다운로드를 하지만 용량을 최소화하여 최대한의 이익을 남김

* 검증헤더
    * 캐시 데이터와 서버 데이터가 같은지 검증하는 데이터
    * Last-Modified, ETag
* 조건부 요청 헤더
    * 검증 헤더로 조건에 따른 분기
    * 조건이 만족하면 200 OK
    * 조건이 만족하지 않으면 304 Not Modified
##### If-Modified-Since : Last-Modified 사용
* 데이터가 이후에 수정되었는지를 확인
* 하지만 이러한 설정에는 단점이 있음
    * 1초 미만 단위로 캐시 조정이 불가능
    * 날짜 기반의 로직 사용
        * 데이터를 수정한 날짜가 다르지만 내용이 같다면 다시 다운로드해야함

##### If-None-Match : ETag 사용
* 날짜 설정의 단점을 보완하기 위해 사용
* 캐시용 데이터에 임의의 고유한 버전 이름을 달아두고 데이터가 변경시 이 이름을 바꾸어서 변경
* 단순히 ETag만 보내서 같으면 캐시 유지, 아니면 다시 다운로드
* 태그가 매치되면 실패, 서버에서 304를 전송

#### 캐시와 조건부 요청 헤더
* Cache-Control : 캐시 지시어
    * Cache-Control: max-age
        * 캐시 유효시간, 초단위
    * Cache-Control: no-cache
        * 데이터는 캐시해도 되지만, 항상 원래의 서버(중간의 캐시서버는 안됨)에 검증하고 사용
    * Cache-Control: no-store
        * 데이터에 민감한 정보가 있으므로 저장하면 안됨(메모리에서 사용 권장)
* Pragma : 캐시 제어(하위호환)
* Expires : 캐시 유효 기간(하위호환)
    * 캐시 만료일을 정확한 날짜로 지정하는데 초단위가 아니기 때문에 유연한 설정이 불가능

### 프록시 캐시
* 원서버에서 캐시를 확인하는 것이 아니라 가까운 거리에 프록시 서버에 캐시를 확인
    * 왜냐면 원서버는 보통 클라이언트와 거리가 멀기 때문에 요청을 확인하는데 시간이 오래 걸림
    * 클라이언트 -> 프록시 서버 -> 원서버
* Cache-Control : 캐시 지시어(기타)
    * Cache-Control: public
        * 응답이 public 캐시에 저장되어도 됨
    * Cache-Control: private
        * 응답이 해당 사용자만을 위한 것으로 프록시 서버에 저장되지 않음, 기본값
    * Cache-Control: s-maxage
        * 프록시 캐시에만 적용되는 max-age값
    * Age: 60(HTTP 헤더)
        * 오리진 서버에서 응답 후 프록시 캐시 내에 머문 시간(초 단위)

### 캐시 무효화
* 민감 정보는 저장하면 안됨
* Cache-Control : no-cache
    * 데이터는 캐시해도 되지만 항상 원서버에서 검증하고 사용
    * 원서버가 순간적으로 단절되어 접근이 불가하면 프록시 캐시가 200 OK로 대답할 수도 있음
* Cache-Control : no-store
    * 데이터에 민감한 정보가 있으므로 저장하면 안됨, 메모리에서만 사용하고 삭제하기
* Cache-Control : must-revalidate
    * 캐시 만료 후 최초 조회시 원서버에 검증 필수
    * 원서버 접근 실패시 반드시 오류가 발생해야함 - 504 Gateway Timeout
    * 캐시 유효 기간이라면 캐시를 사용함
* Pragma : no-cache
    * HTTP 1.0 하위 호환

* 따라서 확실히 캐시 무효화를 하기 위해서는 모두 입력해주면 됨
    * Cache-Control : no-cache, no-store, must-revalidate
    * Pragma : no-cache
